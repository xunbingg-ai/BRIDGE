# feat-001 技术栈决策 —— 需要确认的问题（grill-me 版）

> 说明：这份文档是为非软件工程师（医学生）准备的。每个问题都会解释"为什么重要"和"猜错会怎样"。
> 标注 **✅ 已调研** 的问题，我已经从网上查到了建议答案，你只需要确认或修改；其余问题请你用大白话回答即可。

## A. 谁在用、多少人用（决定规模）

**A1 使用人数**：首期大概多少学生、多少老师会用？
- 选项：10 人以下 / 几十人 / 上百人
- 为什么重要：决定要不要一开始就上复杂的服务器和数据库。
- 猜错的后果：低估了，人一多就卡；高估了，白花时间搭重型设施。
- **✅ 已调研建议**：按几十人并发设计，预留扩展到上百人的路（数据库选型上留好迁移口）。

**A2 部署位置**：系统最终跑在哪里？
- 选项：学校机房 / 云服务器 / 自己电脑 / 还没定
- 为什么重要：影响要不要 Docker、域名、HTTPS、服务器备案这些事。
- 猜错的后果：选了需要专业运维的部署方式，一个医学生维护不动。

**A3 上线时间**：什么时候要给老师和学生演示或正式使用？
- 选项：几周内 / 一两个月 / 半年以上
- 为什么重要：决定骨架能做多简单。
- 猜错的后果：追求完美导致赶不上演示节点。

## B. 使用体验

**B1 使用设备**：学生主要在什么设备上练习？
- 选项：电脑浏览器 / 手机 / 两者都要
- 为什么重要：手机要额外做响应式适配，前端工作量和测试范围不一样。

**B2 界面语言**：网站按钮、菜单、提示这些"外壳"用中文还是英文？
- 注意：题目和病人对话按病例配置（这点需求已定），这里只问界面外壳语言。

**B3 病人回复方式**：AI 病人的回复要"打字机"式逐字出现，还是一次性整段显示？
- **✅ 已调研**：DeepSeek API 支持流式输出（SSE），打字机效果很容易做，成本不变；建议做打字机，更像真实对话。

## C. 数据和账号

**C1 账号创建**：学生和老师的账号怎么来？
- 选项：管理员（老师/开发者）批量创建 / 自己注册 / 先随便填个名字
- 为什么重要：决定登录功能复杂度和账号管理界面要不要做。

**C2 数据量**：首期大概多少个病例？每个病例大概多少道题、多少项检查？
- **✅ 已调研参考**：同类平台（Monash MOVE）首期 20 个案例足够；建议首期 5–20 个病例。SQLite 在这种量级完全够用。

**C3 隐私合规**：学生姓名、练习内容有没有特殊要求？（仅校内使用 / 要脱敏 / 数据不能出学校网络）
- 为什么重要：决定数据库要不要加密、服务器能不能放公有云。

**C4 断点续练**：需求已定（学生中途退出后可继续），进度存服务器端，这个不用再确认。

## D. 预算与维护

**D1 API 预算**：DeepSeek 每个月能接受多少花费？
- 选项：¥10 以下 / ¥100 左右 / 没概念
- **✅ 已调研价格**：DeepSeek V4 Flash 输入约 $0.14/百万 token（缓存命中 $0.0028），输出约 $0.28/百万 token。一次病例练习约消耗几万到几十万 token，粗估每次练习成本在几厘到几毛人民币。月预算 ¥10 大概率够几十人高频练习。

**D2 维护者**：以后主要谁维护这个系统？
- 选项：只有你 / 学校 IT / 没人管
- 为什么重要：直接决定"代码越简单越好"的程度。

**D3 开发环境**：确认一下——你用的是 Windows 电脑，愿意装 Docker 吗？（可选，不影响第一阶段开发）

## E. 技术偏好与未来

**E1 语言偏好**：你对 Python 熟悉吗？JavaScript 完全没接触过也正常。
- 为什么重要：决定推荐"全 Python 单一语言"方案，还是"Python 后端 + JavaScript 前端"方案。

**E2 现有系统**：学校有没有已有的教学平台（Moodle、学习通之类）需要对接？
- 选项：没有 / 有（说明是哪个）

**E3 第二阶段展望**：以后大概率会加什么功能？
- 选项参考：语音输入/播报、正式考试模式、倒计时、更多考站类型、虚拟人形象、批量导入病例
- 为什么重要：避免现在的骨架把未来功能的路堵死（例如选了纯文本架构，以后加语音要重构）。

## 建议回答顺序

最影响技术栈的 5 个问题：**A1（人数）、A3（时间）、C1（账号）、D1（预算）、E1（语言偏好）**。
你可以只回答这 5 个，其余我按调研建议默认处理并在最后给你一份"待确认清单"。
